# Daily edition update — split channel contract

## ChatGPT non-Facebook channel

1. ChatGPT updates only `data/chatgpt/editions/YYYY-MM-DD.json` and `data/chatgpt/index.json`. Facebook Favorites are captured by the desktop Codex local CLI and belong only in `data/facebook/`.
2. Read the fixed `master` HEAD, this file, `config/sources.json`, both schemas, and the current ChatGPT index before processing. Use Asia/Taipei for the edition date and the real execution time for `generated_at`.
3. Read complete public originals for only the configured non-Facebook URLs and queries, following each source's existing time range, limits, and rules. Do not add sources, keywords, exclusions, ranking, or login/paid-wall workarounds. Search snippets or truncated pages are not full reads and must not be summarized as news.
4. Preserve all existing ChatGPT stories, ids, ordering, original text, image URLs/credits, and source report. Deduplicate within this channel by original URL or clearly identical event; retain existing ids and append only verifiable new sources. Append new stories in source acquisition order. Do not perform cross-channel deduplication.
5. Write schema v1 with `date`, real `generated_at`, `is_demo: false`, `stories`, and `source_reports`. Each formal story needs at least one valid original source URL. Keep unknown publication time blank or omit it. Use `source_reports.configured_sources` for per-run captured/included/excluded counts and actual limitation notes; use `complete` only when every planned source was fully checked. Any unavailable or incomplete source makes the report `limited`, with the reason stated. Distinguish no new items from a failed read.
6. Write a concise title and summary for every article, rather than copying its full original into summary. Every newly added non-Facebook story must embed exactly one original/source-provided HTTPS image URL with descriptive alt and source attribution in credit. If no usable source image can be verified, do not add that candidate to stories; count it as excluded in the current source report and note the reason. Existing stories keep their current image object or null unchanged. Do not download files, create temporary image files, or add image blobs to the repository. Do not claim that public images are licensed. A missing or failed remote image is hidden by the reader.
7. Keep the ChatGPT index schema v1, with one entry per date, paths under `data/chatgpt/editions/`, correct story counts/demo flags, newest-first dates, `current` at the newest date, and real `updated_at`. Retain all existing index entries.
8. Validate JSON, schema including formats, unique story ids within this channel edition, date, and index/edition agreement. Check for secrets. Update only the current ChatGPT edition and its index.
9. Write both files atomically with Git Data API against fixed `master`; never use sequential writes or a fallback. Re-read HEAD before ref update. If HEAD changed, reload and merge current content, retry up to three times, then stop. Read back the created commit and current `master` to confirm the update persisted.
10. Report date, story count, ChatGPT status/limitations, and commit SHA. If source reading or writing fails, report that plainly. Do not report success without verifying the resulting files.

Facebook automation is separate: the local CLI writes `data/facebook/` and owns its index. Preserve all historical stories, editions, image references, and files; do not delete or clean them up.

## Fast path (same safety and editorial contract)

See `automation/FAST_PATH.md` for the assessment, commands and connector procedure. These operational optimizations do not authorize a daily run to edit code, configuration, schemas, prompts, frontend assets or Facebook data.

- Resolve `master` once and pin initial reads to that commit SHA, including today's edition (only a confirmed 404 means absent). Group independent reads when the active connector supports it; otherwise use its available individual calls. Do not claim a batch facility that is unavailable. The optional local updater uses at most six concurrent read workers.
- Start the six configured source jobs independently. Assign acquisition positions before starting: configuration array order, then original listing order within a source. Preserve these positions when appending selected new stories; never order by network completion time. Keep list-to-full-original dependencies inside each source job and retain all existing editorial selection limits.
- Use each source's optional `discovery` array, in listed preference order, for approved status/list/archive entrances. These are entrances to the same source, not extra sources or permission to broaden its scope. Unsupported or incomplete listings require an honest limitation note, not invented completeness.
- Skip a full original only when reliable publication metadata proves the item is entirely outside that source's existing time window. Coarse dates, relative times, unknown timezones, and boundary-overlapping dates are not grounds to discard an uncertain candidate. Do not confuse event dates, page update times or sitemap `lastmod` with publication time. Continue listing pagination as needed to establish coverage. Codex status is checked every run; only add a Codex story when `Reset scheduled` has a verifiable scheduled time, retaining the source timezone when provided. If the field is empty, absent or unverifiable, publish no Codex story and record the completed check in `source_reports.configured_sources`. The Decoder retains its previous Taipei calendar-day rule. No common replacement window is introduced.
- Every included candidate still needs a full accessible original read and, for every newly added non-Facebook story, one verified source-provided HTTPS image URL with alt and attribution. A candidate without a usable source image is excluded rather than published with `image:null`. RSS/list snippets are discovery only. Report each source's actual coverage and any failed or incomplete read in the existing notes field. An empty result is not proof of no new items. Preserve previous notes and archive previous report metadata in notes labelled `Previous run (historical, not current status)`; top-level counters/status describe the latest completed run, not cumulative edition size.
- Prefer `automation/validate_chatgpt.py` and the deterministic preparation in `automation/update_chatgpt.py`. Editorial relevance, provenance, complete reading, real publication times and exhaustive secret detection still require review; a passing schema is not evidence of them.
- Create one tree with both file contents inline and the fixed base tree, then one commit, then re-read HEAD immediately before a non-force ref update. Tree, commit and ref depend on each other and must remain ordered. Explicit blobs are permitted if necessary, but never a sequential Contents API fallback. On conflict, re-read at the new SHA and append-merge without deleting/reordering prior stories. If rules, sources or schemas changed, stop and recollect against the new contract. Stop after the initial attempt plus three retries; also stop if Taipei midnight invalidates the run date.
- Read back the created commit and both files at that commit and at a freshly resolved `master`. Verify content and ancestry when master advanced. A failed or ambiguous ref update/read-back is not success, even if an unattached commit exists. A no-change rerun may return `unchanged` without a new commit.
